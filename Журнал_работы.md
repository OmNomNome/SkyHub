# Журнал работы — SkyHub

SkyHub — учебная информационная система авиакомпании: расписание рейсов, пассажиры, билеты, багаж и карта рейсов.
Полное техническое задание лежит в файле `ТЗ.md`.

## План (делаем по этапам)

1. Переименование проекта и подготовка папки ✅
2. Бэкенд: схема Prisma, seed, API (Express)
3. Проверка бэкенда curl-запросами
4. Фронтенд: роли, диаграмма Ганта, карта, схема салона
5. start.bat, README.txt, Docker
6. Финальные проверки и архив `SkyHub.zip`

## 2026-11-17 — Этап 2.2. Бэкенд: схема базы данных

**Что сделано:**
- `backend/prisma/schema.prisma`: 10 моделей. Каждая модель записана в многострочном виде, однострочная запись даёт ошибку P1012.
- Статусы, роли и классы хранятся **строками** с комментарием о допустимых значениях. SQLite в Prisma не поддерживает `enum`, проверка значений будет в `services.js`.
- Связи: у рейса два аэропорта, поэтому связи названы (`"DepartureAirport"` и `"ArrivalAirport"`). Без имён Prisma не понимает, какая связь куда ведёт.
- Каскадное удаление: при удалении рейса удаляются его экипаж и билеты, при удалении билета — его багаж.
- Индексы на частые запросы: рейсы борта по времени (`aircraftId, departureTime`) для проверки пересечений и диаграммы Ганта, рейсы по времени, экипаж по сотруднику.
- **Защита от двойной продажи места на уровне базы:** `@@unique([flightId, seatNumber])`.

**Проверено:**
- `prisma validate` проходит. `prisma db push` создаёт `database/app.db` и генерирует клиент.
- Тест: два билета без места (`NULL`) на одном рейсе база пропускает, а второй билет на то же место `5A` отклоняет с ошибкой `P2002` (нарушение уникальности). После теста база пересоздана чистой.

**Почему так:**
- Уникальность `(flightId, seatNumber)` в базе — вторая линия защиты. Backend и так проверяет, свободно ли место. Но если две стойки регистрации одновременно выберут одно место, проверка в коде у обеих пройдёт, а база пропустит только одну запись. В SQLite `NULL` не равен `NULL`, поэтому билеты без места ограничение не нарушают.

## 2026-11-17 — Этап 2.3. Бэкенд: seed (демо-данные)

**Что сделано:**
- `backend/src/common.js` — общие константы и функции для seed и будущего API: допустимые значения статусов и ролей, схема салона 3+3 (`buildSeats`, `seatZone`), работа со временем по Москве, разворачивание регулярного расписания в даты (`scheduleOccurrences`), формат бирки, расстояние по большому кругу.
- `backend/prisma/seed.js` — генератор данных. Порядок: аэропорты → терминалы → самолёты → сотрудники → регулярные и разовые рейсы → экипаж → пассажиры → билеты → багаж.

**Результат на чистой базе (0,4 с):**
```
аэропорты:      214 (пропущено: без IATA 30, дубли 0, без координат 0)
терминалы:      87
самолёты:       22
сотрудники:     204 (3+4+4+1+26+26+140)
шаблоны рейсов: 40 (20 бортов × туда/обратно)
рейсы:          486 (ARRIVED=86, DEPARTED=5, CHECKIN_OPEN=1, SCHEDULED=394)
экипаж:         2952 назначений на 369 рейсах
пассажиры:      800
билеты:         3638 (BOOKED=2770, CHECKED_IN=868)
багаж:          534 (перевес 43, LOST 5)
TK100001:       рейс SU1023 на завтра, BOOKED, места нет, эконом
```
Повторный запуск выводит «В базе уже есть данные — seed пропущен. Для сброса удалите database\app.db» и ничего не меняет.

**Проверено отдельным скриптом:**
- у всех `BOOKED` нет места, у всех `CHECKED_IN` место есть и совпадает с классом билета (0 нарушений); доля бизнеса 12,4%;
- рейсы одного борта не пересекаются, минимальный перерыв 90 мин;
- у экипажа нет конфликтов с буфером 1 ч, на каждом рейсе ровно 1+1+6; свободными остались 4 пилота и 8 стюардесс (на них можно показать назначение и конфликты);
- у рейсов нет терминалов `international`;
- бирки идут подряд: `BAG-2026-000001 … BAG-2026-000534`, номер равен `id`;
- у всех 800 пассажиров род фамилии, имени и отчества согласован;
- два запуска на чистой базе дают одинаковые ФИО, паспорта, номера и время рейсов (совпал хэш данных).

**Почему так:**
- **ГПСЧ mulberry32 с фиксированным зерном** вместо `Math.random()`. С ним данные каждый раз одинаковые: можно написать в отчёте «билет TK100001 у Осиповой Е. Н.», и это будет правдой после любого пересоздания базы. Меняются только даты (расписание строится от сегодняшнего дня) и статусы, которые зависят от текущего времени.
- **Весь seed в одной транзакции** (`prisma.$transaction(async tx => ...)`). Seed пропускается, если аэропорты уже есть. Без транзакции ошибка на середине оставила бы аэропорты без рейсов, и следующий запуск решил бы, что всё готово. С транзакцией при ошибке не записывается ничего.
- **Время расписания считается по Москве (UTC+3).** В базе всё хранится в UTC. Если брать часовой пояс компьютера, в Docker-контейнере (там UTC) рейс «10:00» оказался бы в 13:00 по Москве. В России с 2014 года нет перехода на летнее время, поэтому фиксированный сдвиг +3 ч корректен.
- **Вылет «туда» между 05:00 и 13:00.** Самый длинный рейс (4500 км) длится около 6,5 ч, плюс 90 мин на разворот. Тогда обратный рейс всегда вылетает в тот же день, не позже 21:00, и дни недели у обоих рейсов пары совпадают.
- **TK100001** выдаётся на ближайший рейс, который вылетает **не раньше чем через сутки**, а не просто на ближайший будущий. Иначе демо, запущенное через пару часов после seed, попало бы на рейс, который уже улетел. Класс у него эконом, чтобы на схеме салона было видно, что бизнес-ряды для него закрыты.
- **Женская форма фамилии строится по правилам** (`-ов → -ова`, `-ский → -ская`, `Шевченко` и `Черных` не меняются), а не хранится отдельным списком. Так список фамилий короче, а ошибок «Иванов Мария» нет.
- Номер бирки равен `id` записи. Тогда генератор в API (`max(id)+1`) продолжит нумерацию без пропусков и дублей.
- Статусы самолётов в seed все `READY`. `IN_FLIGHT` не проставляем автоматически: создавать рейсы разрешено только на `READY`-бортах, и с автоматическим `IN_FLIGHT` диспетчер не смог бы планировать будущие рейсы борта, пока тот в воздухе.

## 2026-11-17 — Этап 2.4. Бэкенд: API

**Что сделано:**
- `backend/src/index.js` — запуск Express. Сначала читается `backend/.env` встроенной функцией `process.loadEnvFile` (пакет `dotenv` не нужен). Если есть `backend/public` (сборка фронтенда, так будет в Docker), раздаётся ещё и она. Здесь же единый обработчик ошибок: ответ всегда `{ "error": "текст" }`.
- `backend/src/routes.js` — все маршруты, контроллеры в одну строку.
- `backend/src/services.js` — вся бизнес-логика и проверки.
- `backend/tests/api-check.js` — автотест API на 55 проверок (пункт 9 ТЗ и сверх него).

**Маршруты (префикс `/api`):**

| Раздел | Маршруты |
|---|---|
| Самолёты | `GET/POST /aircraft`, `PUT/DELETE /aircraft/:id` (`?status=READY`) |
| Аэропорты | `GET/POST /airports` (`?q=`), `PUT/DELETE /airports/:id`, `GET /terminals` (`?q=&airportId=`) |
| Сотрудники | `GET/POST /users` (`?role=PILOT,COPILOT&q=`), `PUT/DELETE /users/:id` |
| Рейсы | `GET /flights` (`?from=&to=` — для Ганта и карты), `POST /flights` (разовый или `isRegular: true`), `GET /flights/:id`, `PATCH /flights/:id/status` |
| Экипаж | `GET /flights/:id/crew-candidates` (кто свободен/занят), `PUT /flights/:id/crew`, `DELETE /flights/:id/crew` |
| Салон | `GET /flights/:id/seats` (все места: зона и занятость) |
| Билеты | `GET /passengers`, `GET /tickets` (`?q=` номер/паспорт/ФИО), `GET /tickets/:id`, `PATCH /tickets/:id/checkin`, `POST /tickets/:id/baggage` |
| Багаж | `GET /baggage` (`?flightId=&status=&tag=`), `PATCH /baggage/:id/status` |

**Главные правила, которые проверяет backend:**
- Регистрация: место обязательно (400), место должно существовать в салоне (400), быть своего класса (409) и свободным (409). Класс билета не меняется. Уже зарегистрированному пассажиру место можно сменить.
- Создание рейса: борт `MAINTENANCE` → 409, борт не `READY` → 409, пересечение с другим рейсом борта → 409 с номером и временем мешающего рейса. Регулярный рейс разворачивается в даты; занятые и прошедшие даты пропускаются и перечисляются в ответе. Если не создано ни одного рейса → 409.
- Экипаж: ровно 1+1+6, роль сотрудника совпадает с местом в экипаже, конфликт → 409 с ФИО и номером рейса. Буфер 1 ч считается от вылета и прилёта, то есть учитывает время полёта.
- Статусы рейса: `SCHEDULED → CHECKIN_OPEN → DEPARTED → ARRIVED`, отмена из `SCHEDULED/CHECKIN_OPEN`, всё остальное → 409.
- Багаж: только у зарегистрированного пассажира и до вылета. Бирка генерируется сервером (`max(id)+1`). Перевес не блокирует оформление, но в ответе приходит `warning`.
- Админ: нельзя удалить самолёт, аэропорт или сотрудника со связанными рейсами (409). Нельзя изменить салон самолёта так, что зарегистрированные пассажиры останутся без места.

**Результат проверки:** `node tests/api-check.js` — **все 55 проверок пройдены**. Выдержка:
```
OK [200] GET /tickets?q=TK100001 (seatNumber = null)
OK [400] PATCH checkin без места
OK [409] PATCH checkin 1A «Место 1A — бизнес-класс, а билет TK100001 — эконом-класс…»
OK [409] PATCH checkin 22A «Место 22A уже занято (билет TK100002)»
OK [200] PATCH checkin верное место
OK [201] POST багаж 30 кг «Перевес: багаж 30 кг при норме 23 кг…», бирка BAG-2026-000535
OK [409] POST рейс на занятом борту «Самолёт RA-73012 занят: рейс SU1023 18.11 18:15–23:25 МСК…»
OK [409] POST рейс на борту MAINTENANCE
OK [409] PUT экипаж «Конфликт экипажа: Миронов Д. Е. — рейс SU1023 … перерыв не менее 1 ч»
OK [409] PATCH рейс SCHEDULED → ARRIVED
```
После тестов база пересоздана чистой: тест меняет данные, например регистрирует TK100001.

**Почему так:**
- **Проверки в `services.js`, а не в маршрутах.** Маршрут только передаёт параметры, поэтому все правила лежат в одном файле, и их легко найти и прочитать. Ошибка — это `throw new ApiError(409, 'текст')`, а один обработчик в `index.js` превращает её в `{ error }`.
- **Поиск по ФИО идёт в JavaScript, а не через SQL `LIKE`.** В SQLite `LIKE` без учёта регистра работает только для латиницы: «иванов» не нашёл бы «Иванов». 800 пассажиров фильтруются в памяти за доли миллисекунды.
- **Ограничения в базе как страховка.** Уникальность места и номера бирки защищает от гонки, когда два запроса одновременно прошли проверку в коде. Обработчик ошибок переводит `P2002` в понятный 409 («Это место уже занято»).
- **`DEPARTED` без полного экипажа запрещён.** В ТЗ этого нет, но самолёт без пилота улететь не может. В демо экипаж назначается раньше вылета, так что сценарий не ломается.
- **Сделал сверх ТЗ:** `crew-candidates` показывает для каждого члена экипажа, свободен ли он, — фронтенду не придётся угадывать, кого можно назначить. `seats` отдаёт готовую схему салона с зонами и занятостью.
- **Время в сообщениях об ошибках — по Москве** («18.11 18:15–23:25 МСК»). Если прилёт на следующий день, у него тоже указана дата («20.11 23:55–21.11 01:25»).

**Проблемы, найденные при проверке, и как решены:**
1. **`react-calendar-timeline` не находил `interactjs` и `prop-types`.** В этой библиотеке они объявлены как peer-зависимости, а с флагом `--legacy-peer-deps` npm их не ставит. Добавил оба пакета в `package.json` явно. По той же причине явно указан `@ant-design/icons`: раньше он попадал в проект только как зависимость antd.
2. **http://localhost:5173 не открывался.** Vite слушал только IPv6 (`::1`), а `localhost` на этом компьютере резолвится в IPv4 `127.0.0.1`. В `vite.config.js` задал `host: '127.0.0.1'`, прокси `/api` тоже идёт на `127.0.0.1:3000`.
3. **Заголовок дня на диаграмме был на английском** («Tuesday, November 17»). moment-локаль не доходит до копии moment внутри библиотеки, поэтому подпись дня форматирую сам через dayjs: «вторник, 17 ноября 2026».
4. **Предупреждения React в консоли из моего кода:** `defaultTimeStart` должен быть moment-объектом, а `key` нельзя передавать через `{...spread}`. Оба исправлены.
5. **Бесконечная загрузка в CrudTable.** Функция `load` создавалась заново при каждом рендере. Нашёл при вычитке кода до запуска и исправил через `useRef`.
6. **В недельном режиме подпись дня сливалась с фоном** (белый текст на светлом). Задал тёмный фон явно.

**Почему так:**
- **Всё время в интерфейсе — МСК**, как и в расписании на backend. Шкала Ганта сдвигается на разницу между поясом браузера и МСК, поэтому пользователь в Новосибирске увидит то же время, что диспетчер в Москве.
- **Занятых членов экипажа не блокирую в списке, а помечаю.** По демо-сценарию нужно уметь выбрать занятого пилота и увидеть ошибку. Финальная проверка всё равно на backend.
- **«Зарегистрировать» неактивна, пока место не выбрано.** Чужой класс и занятые места на схеме не кликаются, но backend тоже проверяет: это защита на случай запроса в обход интерфейса.
- **Бирка печатается в отдельном окне.** Тогда на печать уходит только бирка, без всей страницы, и не нужны сложные print-стили.
